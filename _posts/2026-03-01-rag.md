# Vector Database 

Databases come in various forms for example, key-value (dictionary) store, document store, graph database, columnar store. Vector database is one form that saves information as multidimensional vectors, an organized store of vector embeddings of data. 

A vector database is one that indexes and stores vector embeddings for fast retrieval of data by similarity search or vector search. Vector databases like pinecone is commercially available, while popular open-source ones are chroma, weaviate, and qdrant. Elastic search is one widely deployed vector database, another one lanceDB is open-source but offers commercial products with additional features and managed services. 

<img width="499" height="158" alt="vdb" src="https://github.com/user-attachments/assets/3fce8c01-b0de-4ac9-99bf-7995a1b8f5af" />


Vector databases are designed for efficiency and scalability, unlike traditional keyword-matching databases. Key differences between vector dayabase and traditional database are as follows.

1. Vector databases are optimized for vectorized data storage and retrieval while traditional databases are optimized for scalar values.

2, Vector databases efficiently handle high-dimensional data.

3. Vector databases have advanced indexing and query techniques for similarity search, traditional databases have simple indexing method only.

4. Vector databases are designed for seamless integration with machine learning (ML), and traditional databases have limited compatibility with ML workflows. 

Vector databases usually maintain two indices, a vector index and a metadata index. It performs the metadata filtering either before or after the vector search. 

The [embedding models](https://www.nvidia.com/en-us/glossary/vector-database/) utilized for vectorization of the input data based on their types (text, image, audio, video). are neural networks with transformer architecture. 

<img width="433" height="290" alt="embed" src="https://github.com/user-attachments/assets/c255f3d0-1d56-4955-8cc2-8b13fd692d6b" />


Vector databases are immensely useful as semantic search engines and for [recommendation systems](https://www.linkedin.com/posts/drranja-sarkar_recommenders-amazon-knowledgegraphs-activity-7305128847052562433--Hvl) leveraging user-item similarity (collaborative filtering).

VdBs use distances (e.g. Euclidean, cosine similarity) in the embedding space to represent (semantic) similarity between query vector and vectors in the database for information retrieval. 

 In contrast to traditional keyword search, vector search offers a more flexible and optimized way of searching.

 The query/prompt (as an embedded vector) is used for semantic search through clustering algorithms to arrive at relevant output/result.

# RAG 

Vector databases enhance the capability of an LLM by supporting with memory, that is helping the model remember what was said earlier to hold a proper conversation with the prompt and with factual information outside of the general knowhow. This is called retrieval-augmented generation (RAG). 

A RAG system typically has a retrieval component linked to a knowledge-base which is typically a pre-trained LLM, and a generative component. VdBs can effectively provide LLMs with state by updating the information, without which the (trained) model knowledge is frozen.

The retrieve-generate process can be broadly of 3 types:

i) iterative

ii) recursive

The adaptive method enhances the RAG pipeline, as it can be either model-based or rule-based. Adaptive RAG produces the best results owing to its flexible and active control of the process. How you retrieve the relevant information dictates how much better is your LLM application.

In RAG with a vector database called vectorRAG the vector similarity search is utilized which is identification of text chunks having similarity with input text. Vector search uses algorithms like cosine similarity for comparing the distance between the encoded-as-a-vector user input (query) and the embedded-as-vectors text chunks and identifying the relevance. The RAG app returns top 5 or 10 similar chunks or documents to provide context to the LLM. The vector (semantic) search however might not be sufficient in some cases, like when the LLM needs information from multiple documents or text chunks for generating an accurate answer to a complex user query. This is where graph databases are better. 

If one moves outside the general knowledge into domain-specific areas where the relevant facts may not have been a part of model training, LLMs start to “hallucinate”. Here’s where RAG by VdB comes in handy. 


💡How does one reduce LLM hallucinations? 

One uses a vector search engine to retrieve relevant information and pipe it to the LLM’s context window for factually accurate results. RAG gives LLMs access to new information via vector databases and graph databases. 

Given the probabilistic paradigm, one can only reduce hallucinations and not get rid of them completely.

Popular open-source frameworks to support the creation of LLM applications with RAG are LangChain, LlamaIndex. 

LangChain typically has four components: chain (workflow), index (mapping to data storage location), memory (saving capacity), and prompt (instruction/query). 

An open-source framework to evaluate LLMs is [DeepEval](https://deepeval.com). A human-in-the-loop for validating LLM output wrt user expectations is crucial. 
---

In vector databases, vector similarity is used however, data stored in graph databases is better suited to reduce hallucinations and answer complex queries with more relevance and accuracy, due to the ability of graph-structured data to provide the complex relationships between data objects. This is why systems leveraging graphRAG are on the rise. 

Knowledge graphs and graph databases store data as a network of nodes (entities) and their relationships (edges). A graph data structure allows navigation from one piece of information to another efficiently, accessing all related information and improving query efficiency. 
 One can dump structured as well as unstructured data into the graph database without having to re-design the schema. The constructed knowledge graphs from text, tabular data, etc. are thrown into the database. By processing each node and its edges with other nodes and connecting them, one can have a structured representation of all information. This flexible approach allows for easier traversal and navigation through inter-connected documents, enabling proper reasoning to answer complex queries or multi-part questions. Also, constructing knowledge graph during the ingestion phase reduces workload during query time, thereby improving latency.
